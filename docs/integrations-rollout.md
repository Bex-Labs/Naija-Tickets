Signing rotation: add the new active version while retaining the bounded previous versions needed for still-valid checkout/widget proofs; remove only after expiry and verification. Encryption rotation: retain versions needed to decrypt every active endpoint until each endpoint is explicitly rotated/retired. Removing a needed version interrupts dispatch. Endpoint rotation does not expose the old secret again; coordinate it with the receiver. API rotation invalidates the old key according to the existing organiser flow; replace it only in server-side partner environments.

## Public acceptance sequence

1. Open the public schema and all developer guides. Missing key → 401, browser Origin → 403 where documented, unrelated event/application → safe denial. Revoke a test key and confirm immediate failure. Test app suspension/restore with fresh credentials and paused settings; do not suspend a real business for a demo.
2. From Partner Demo, create a hosted session with a unique idempotency key. Repeat creation to confirm one reservation; change payload under the same key to confirm conflict. Keep secrets on the partner server. Complete Paystack test payment using provider-supported test details, return through the sandbox callback and then Partner Demo, and independently read verified status before displaying success. URL parameters alone cannot prove payment.
3. Confirm issued ordinary tickets and account history. Check free checkout, expired sessions, cancellation/released unpaid hold, group package/admission counts, unclaimed slot reservation, duplicate-contact denial, unique claimed QR and one-time entry. Use the existing admin workflow for a provider-verified test refund, then verify entry/status/history. No real charge or live payout is appropriate.
4. Repeat through the public widget with exact origin/event restriction. Check mobile selection, top-level payment return, keyboard interaction, narrow widths, Safari and blocked third-party cookies; no usable QR before group claim. An unregistered embedding origin must fail frame-ancestors and cannot obtain a checkout by spoofing a URL parameter.
5. Configure a dedicated durable public receiver. Verify raw-body HMAC/timestamp/header-body agreement/app/mode; durably insert event ID and payload hash before 2xx. Exact duplicates acknowledge once; conflicting bodies deny; invalid signatures/large/stale requests deny. A handler that only prints or stores in process memory is not accepted. Partner Demo's current disabled receiver must not be marked delivered.
6. Observe actual scheduled delivery and one recovery/retry on the public sandbox. Current Hobby schedule: daily 04:00 UTC, at most 20 attempts per invocation including retries; timing is not exact and Vercel does not automatically retry failed cron invocations. See [Vercel limits](https://vercel.com/docs/cron-jobs/usage-and-pricing) and [cron management](https://vercel.com/docs/cron-jobs/manage-cron-jobs). Manual retry queues work for a later dispatcher; it does not promise immediate delivery. Do not certify scheduled acceptance from a manual call.
7. Record non-sensitive evidence per gate with exact deployment origin/environment and verifiedAt. Run `npm run integrations:readiness`. Disabled/pending/fail means not ready for the full platform, even if basic reads work. This local checker does not contact the provider or attest evidence. Complete a risk/throughput review with expected venue/partner traffic; current bounded concurrency tests are not an SLA.

## Monitor and recover

Review private admin Integrations totals, last-24h authenticated errors, request IDs/latency, organiser delivery history, exhausted jobs, oldest queued work, cron execution/failure and database growth. Public widget/unknown-key rejections require safe infrastructure logs. Investigate increasing latency, 429/503, missing cron, sustained backlog or payment/issuance mismatches before expanding access. Do not store payloads, authorization headers, QR codes or private links in monitoring.

A receiver may accept a job before its acknowledgement is lost; expect at-least-once delivery and deduplicate durably. Payment and admission idempotency remain in the existing database engine. Inspect stored verified payment/issuance and API status rather than issuing replacement tickets or repeating a provider charge from a redirect.

For abuse, suspend the particular application through the password-confirmed admin action. For infrastructure failure, turn off the affected integration feature and redeploy after approved configuration change; preserve provider callbacks and already-authorised payment finalisation. Stop advertising new checkout while repairing its prerequisites. Paused dispatch preserves durable work but does not undo accepted notifications.

Prefer a forward schema fix. If code rollback is needed, verify old code's compatibility with the additive schema and review admin-cookie/hash-format compatibility first: pre-Phase-7 authentication code cannot verify upgraded scrypt hashes. Do not roll back stored passwords to old hashes, drop migration tables or reset the database. Keep the current authentication module or deploy a tested forward fix. Reconcile any reserved/paid sessions through the existing engine before reopening purchases.

No automatic log/outbox/attempt/audit purge is added. Before broad launch, choose documented retention, storage monitoring and a separately reviewed bounded archival/purge process that preserves financial/security records and deduplication guarantees. Entry replay rows have seven-day expiry with bounded cleanup and a per-app cap; this is separate from durable webhook retention. Never run broad deletions to clear a delivery backlog. Keep prior evidence and update progress with actual remaining limits.
