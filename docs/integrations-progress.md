## Phase 6 report

**Phase completed locally:** Advanced API operations. The user explicitly chose to proceed before the earlier public sandbox purchase/deployment gates. Those gates remain incomplete. Phase 7 has not started.

**Features:** Nine route patterns provide application-attributed order list/details, purchased ticket list/status, permitted attendee names/contact, sales summaries, group registration counts, recorded refunds and delegated verification/check-in. Uses the same orders, sessions, payments, ticket records, group claim engine, venue entry lock/check-in table, refund recorder and Phase 4 outbox. Each resource requires reciprocal session/order attribution, matching application/mode/event/organiser and a current event grant. Another application of the same organiser and ordinary marketplace purchases are excluded. Ended/unpublished event history remains readable with current grants. Partner entry additionally requires a published event that has not ended; no earliest entry time is added and the ordinary venue routine is unchanged.

**Permissions and privacy:** New opt-in scopes: tickets:status, attendees:read, attendees:contact, sales:read, groups:read, refunds:read, entry:verify and entry:check-in. Existing orders:read expands to minimal attributed order data; existing keys receive no new scopes. Ticket type reads remain tickets:read. Contact fields require both attendee scopes; unclaimed slots are excluded from attendee lists and erased identities return null even with contact permission. No buyer contact, receipt reference, QR/display code/hash, invitation/private member token, payment capability or provider/admin payload is returned. Both the database and server project explicit fields. API keys are server-only; browser Origin, foreign widget IDs, missing permissions, invalid methods and malformed/duplicate queries fail closed. Cursor binding includes application/mode/permissions/operation/resource/filter. Lists are bounded to 20 default/100 maximum and ordered by resource UUID ascending, not purchase date.

**Delegation and idempotency:** The current key creator is the sole delegated entry principal, with current management membership and owning-organiser/event authority. A partner cannot supply a staff/customer actor, assign staff or scan other applications' tickets. Verification requires entry:verify; admission also requires entry:check-in. The existing verify_event_entry function locks and updates the ordinary order/ticket/check_ins records, rejects unpaid/refunded/used tickets, and triggers the existing outgoing event. The adapter additionally requires matching verified payment amount/currency/timestamp. Independent unique admission rows still enforce one entry per claimed admission. A private seven-day idempotency record replays the original minimal outcome without repeating entry; different code/event/action conflicts, new scans of used tickets report already_used, and revocation/grant loss is checked before replay. Replayed admitted outcomes are historical results, not current validity proof. Extra budgets are 30 entry requests/key/minute and 120/organiser, within existing shared limits. Retained requests are capped at 10,000/application with bounded expired-row cleanup. No event-scale throughput/offline scanning guarantee is claimed.

**Financial meaning:** Sales are only this application's attributed verified purchases; unpaid/failed reservations do not count. Original discounted ticket subtotal, service fees, customer payments, completed refunds and net customer receipts are separately labelled. Sold admissions count valid/used records of currently paid/partially-refunded verified orders, including unclaimed group slots. Totals are not payouts, settlement or inferred platform/organiser cash balance. Refund API is read-only. Group API reports registration/claimable counts without forwarding bearer invitations or claiming on attendees' behalf. Existing buyer/attendee claims and admin provider-verified refund recording remain the supported writes. No new partner cancellation, admin refund initiation or group-claim/QR export bypass is advertised.

**Files/database:** Adds `202610160003_integration_operations.sql`, `lib/integrations/operations{,.server}.ts`, nine `/api/v1` routes, two operation test files and their disposable fixture. Extends scope/route metadata, organiser key-permission descriptions, optional shared RPC error mapping, introspection configuration flags, safe `.env.example`, existing independent PostgreSQL harness, README and these docs.
